# 个人地址簿存储与迁移

适用范围：本仓库的官方 RustDesk 1.4.9 相关协议和旧版个人地址簿。

`AddressBookStore` 是地址簿的唯一读写入口。完整 JSON 文档是权威数据，
`api_address_book_entry` 是可重建索引，不再决定是否显示快照中的条目。
每个账户有持久化 GUID 和递增 revision；每条 Peer 有稳定 entryId，
RustDesk ID 可以修改。导入其他账户的文档会分配本账户的条目身份，
不会借用其他账户的索引主键。旧版上传不带内部身份时，同 Peer 保留原 entryId。

Web 修改必须携带读取时的 revision，缺失或过期返回 409
`address_book_revision_conflict`。草稿保留开始编辑时的版本，刷新列表不会
升级旧草稿。原生 Bearer 的旧版整本上传保持整体替换语义；部分修改在当前
revision 上执行事务 CAS。文档、revision 和索引在同一事务提交。

迁移版本 3 在 SQLite 写锁内执行。旧快照与索引取并集；只有索引的
updated_at 严格晚于快照时才采用索引的已知字段，同时间优先快照。
未知连接字段保留。SQLite 时间和带时区 RFC3339 时间均转换为 UTC 比较。
重复 Peer ID、重复条目身份、相互矛盾的身份别名、损坏 JSON/字段/颜色/
时间或无法合并的身份冲突会回滚整笔迁移，并报告账户和冲突原因。
启动重试不会留下部分迁移或重新分配已有 GUID。

发布前迁移步骤：

1. 停止所有数据库写入者（hbbs 和 API）；用 SQLite 一致性备份机制保存
   数据库，保存当前程序版本、RustDesk 密钥和独立 OAuth 配置密钥。
2. 在隔离目录对备份副本执行 SQLite integrity_check，并以新程序执行迁移预检。
   配置临时回环监听、独立端口；禁止副本连接生产 OAuth 或用户流量。
3. 检查迁移报告、各账户条目/标签及未知字段，验证 revision、GUID 和索引一致。
   冲突必须人工确认修复来源数据后再次预检，不能删除冲突条目后假称无损。
4. 副本预检和实机发布门禁通过后，才在维护窗口升级实际数据库及匹配的 hbbs/API。

回滚必须停止新版本写入，恢复升级前的数据库一致性备份、配置密钥和
匹配程序版本。禁止仅回退镜像后让旧程序继续写已经迁移的文档。
本轮自动化测试只迁移临时数据库，不执行上述生产步骤。
